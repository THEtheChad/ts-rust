# B8: the file system of a checker worker (`WORKER_FS`)

Lane B8 checks the suspect in `program/go_frontend.rs`: a checker worker thread answers
`Program.FileExists` from `WORKER_FS`, a per-thread OS file system, where Go asks the program
host's file system. That host is the CLI's OS file system, the language server snapshot (with the
open documents), or the API's request or callback file system.

## How Go does it at the pin

- `compiler/program.go:146` `(*Program).FileExists` returns `p.Host().FS().FileExists(path)`. The
  host's FS is a `cachedvfs.FS` (`compiler/host.go:52`), shared by every checker goroutine.
- Its checker-side callers:
  - `modulespecifiers/util.go:184` `tryGetAnyFileFromPath`, through the module specifier host
    (`program.go` implements it). It runs from `processEnding` when the ending is minimal and the
    target is an `index` file: is there a file next to the directory?
  - `checker/checker.go:15860` `getSuggestedImportExtension`, the TS2835 suggestion of an
    extensionless relative ESM import under node16 or nodenext.
- Module specifier generation also reads package.json files, through `GetPackageJsonInfo` and
  `GetNearestAncestorDirectoryWithPackageJson` (`program.go:169`, `:178`). Both use the program's
  resolver, which reads the same host file system.
- `api/session.go:4120` `emitProgram` calls `program.Emit`. For a project program,
  `compiler/program.go:1903` `Emit` gets each file's checker from the program's checker pool
  (`newEmitHost`), the project pool that the diagnostics use.
- `execute/watcher.go:480`: a full `tsc --watch` build uses `trackingvfs.FS{Inner: cached}` as the
  host FS. Every `FileExists` call through it, the checkers' included, adds the path to
  `SeenFiles`. A change to a seen path that is not a source file forces a full build (`:338`).

## Every path that reaches `WORKER_FS`

`WORKER_FS` has one reader: the worker branch of `go_frontend::file_exists`, which runs when
`FRONTENDS` on this thread has no entry for the current program. Callers of
`program::file_exists`:

| caller | Go counterpart | which threads reach `WORKER_FS` | Go's FS there |
|---|---|---|---|
| `ProgramHost::file_exists` → `modulespecifiers::util::try_get_any_file_from_path` (`specifiers.rs:888`) | `util.go:184` via `Program.FileExists` | CLI checker workers, emit pool and d.ts twins (declaration emit, declaration diagnostics, type text in errors); **API emit** (`program_emit::emit` on the compile pool); LSP search threads | CLI: OS (watch full build: tracking FS over it); API: the snapshot FS (request or callback FS) |
| `Checker::get_suggested_import_extension` (`checker_p17.rs:1133`) | `checker.go:15860` | the same threads: the check of a node16/nodenext file, including `noEmitOnError`'s diagnostics inside the API emit | the same |
| `checker_access.rs:221`, `:232`; `go_frontend.rs:2889` | none | `#[cfg(test)]` only | |

The same thread split holds for the package.json lookups of module specifier generation. They are
not `WORKER_FS`, but they have the same flaw: `modulespecifiers/host.rs`
`get_package_json_info_for_directory` reads `osvfs_fs()` off the loading thread, where Go's
resolver reads the host FS. That file belongs to lane B7, so B8 did not edit it. The fix below
takes the API emit off the worker threads, so these lookups move too.

The threads, by process:
- **`tsc`, `tsc -b`, `tsc -w`:** checks and emit run on checker workers, the emit pool and d.ts
  twins. The host FS is the OS FS (bundled-wrapped), the same thing `WORKER_FS` reads, apart from
  the cache, which `HostFsCache` supplies, and the tracking of a watch full build, which was
  missing (below).
- **Language server:** every check runs on the dispatch thread (`project/checkerpool.rs`,
  `ls_program::CompilerCheckerPool`). That thread loaded the program, so `FRONTENDS` answers from
  the snapshot FS. Search threads (`ls/search_thread.rs`: cross-project references, implementations
  and rename) reach `WORKER_FS`. Those requests make no module specifier, and the search checker's
  diagnostics are never reported, so no answer depends on it.
- **API:** the diagnostics methods run on the dispatch thread (`ls_program`). Before this lane,
  `emit`, `emitToString` and the selected-files emits ran `program_emit::emit` on the compile pool,
  which is `WORKER_FS`. The build orchestrator checks on compile workers, over the session's
  `snapshotHost.FS()`. That FS is the OS FS unless the client enabled callbacks; then Go asks the
  client and tsc-rs still asks the OS. The harness enables no callbacks, so this case has no test.

## The fix

1. **The API emit uses the program's own checkers** (`de58e8387`). `api/session_p2.rs`
   `emit_program` and `handle_emit` call `ls_program::emit` and its new per-file form,
   `ls_program::emit_file_results`, instead of `program_emit::emit` on the compile pool. This is
   Go's `Program.Emit` of a project program: the program's checker pool, shared with the
   diagnostics, on the thread that holds the program's host. The emit's probes then ask the
   snapshot FS, and so do its package.json lookups (the loading-thread branch of
   `ProgramHost::get_package_json_info`). The emit also uses the checkers that the diagnostics
   requests warmed, as Go's does.
2. **Watch tracks the workers' probes** (`42829498b`). `program::track_worker_file_probes` marks the
   full-build version of `tsc -w`. A worker's miss in `HostFsCache` then notes the path in
   `VersionTables::worker_seen_files`, and the watcher adds the noted paths to `tfs.seen_files`,
   next to the package.json entries that it already added. A path is noted only on a cache miss,
   which loses nothing: the set and the cache hold the same paths.
3. **`WORKER_FS` stays.** After 1, its only users are programs whose host FS is the OS FS (the CLI
   and API build orchestrator without callbacks). A worker needs a per-thread `Rc<dyn Fs>`, and
   `WORKER_FS` is that. Its doc and `file_exists`'s comment now say which hosts reach it, and name
   the two remaining cases that do not ask the program's host: search threads, which change no
   answer, and the callback build orchestrator, which no test covers.
   - **Not done:** a thread-safe view of every host FS (snapshot, request, callback, overlay),
     which would let any worker ask the right host. It would add a method to the `Fs` trait and to
     about 20 implementations. A callback FS can only be asked from the dispatch thread anyway, so
     that would need a proxy that serves queries inside every wait of the loading thread. That is
     not cheap, and it fixes no observable difference.

No switch was added or removed.
