# B7: project-reference symlink redirects (ts#64519; B3 risk 7, F4)

Lane B7 checks B3's risk 7 (`audits/b3-prepin.md` §4 F4). tsc-rs kept the shape that
`get_source_to_dts_if_symlink` had before ts#64519. The questions are whether that shape fills the
symlink map at other times or in another order than Go at the pin `3e9236361fa9`, and whether
anything observable differs.

## How Go does it at the pin

- **Files:** `compiler/projectreferencefilemapper.go`, `projectreferenceparser.go`, `fileloader.go`,
  `filesparser.go`, `projectreferencedtsfakinghost.go` and `program.go`.
- **Two types.**
  - `projectReferenceFileMapper` (`:12`) is the program's. It only reads: `getParseFileRedirect`
    (`:45`), `getRedirectForResolution` (`:100`), `getCompilerOptionsForFile` (`:90`) and the rest.
  - `projectReferenceFileMapperBuilder` (`:26`) embeds it and adds `host`. It exists only while the
    program loads, as `fileLoader.projectReferences`.
- **Construction** (`fileLoader.addProjectReferenceTasks`, `fileloader.go:341`). The loader always
  makes the builder, with `config`, `useSourceOfProjectReference = opts.canUseProjectReferenceSource()`
  and `host = &compilerResolutionHost{p.host, Config.BaseDirectory()}`. With no references it returns
  there.
- **Filling the static maps** (`projectReferenceParser.parse`, then `initMapper`,
  `projectreferenceparser.go:69`). This runs once, before any file task:
  - `configToProjectReference`, `referencesInConfigFile`;
  - `sourceToProjectReference` and `outputDtsToProjectReference`: each task's maps are copied
    before its subtasks', so a child overwrites a parent;
  - `dtsDirectories`, only when the program uses the sources of its references.

  `initMapper` then sets `builder.host = mapper.resolutionHost(builder.host)` (`:31`). That is the
  d.ts-faking host when the sources are used and there are output entries, else the same host. The
  loader's module resolver gets that host (`fileloader.go:196`).
- **Filling `realpathDtsToSource`.** Only the builder's `resolveSymlink` (`:197`) fills it, lazily,
  while files load. It is called from:
  - `builder.getParseFileRedirect` (`:173`): only when the sources are used and the file has no
    output-dts entry. Each parse task calls it first (`filesparser.go:73`);
  - `builder.getRedirectForResolution` (`:180`): only when the file has neither a source nor an
    output-dts entry. Through it, `getCompilerOptionsForFile` (parse options, `fileloader.go:417`),
    `getRedirectParsedCommandLineForResolution` (`:919`, the JS-file check of a resolved module)
    and the import and type-reference resolution of each file (`:783`, `:838`) call it too.
  - `resolveSymlink` returns if `path` already has an entry. Otherwise it does something only when
    `len(ResolvedProjectReferencePaths()) != 0 && preserveSymlinks`:
    - a file name without `/node_modules/` stores nil;
    - else it takes `host.FS().Realpath(fileName)`; equal to the path, it stores nil; else it
      stores `getProjectReferenceFromOutputDts(realPath)`, which may be nil.

    The host is the builder's, so it is the faking host when that is in use.
- **After the load** the program keeps only the mapper (`filesparser.go:577`). Every later lookup
  (`program.go:216`–`258`, `:495`, `:512`, `:1781`–`:1814`) only `Load`s `realpathDtsToSource`. A
  file the load never asked about has no entry, and nothing adds one.
- **Order of effects**, for one file: the parse redirect, then the parse options, then the
  resolutions of its imports. The first call that reaches `resolveSymlink` decides the entry, and
  every later call reads it. The CLI never uses the sources of references, so there only
  `getRedirectForResolution` fills the map. The project service (LSP and API) uses them, so there
  `getParseFileRedirect` fills it first and redirects a symlinked output `.d.ts` to its source.

## The Rust shape before this lane (`7ac727c70`)

- **One type.** `ProjectReferenceFileMapper` had `host: Option<..>` and `loader: Option<MapperLoader>`.
  They were set while a program with references loads and cleared at the end of the load, which also
  broke the mapper → host → faking vfs → mapper cycle.
- **The pre-split function.** `get_source_to_dts_if_symlink` (Go `getSourceToDtsIfSymlink`, removed
  by ts#64519) read the map, and while `loader` was set it also filled it. The mapper's own
  `get_parse_file_redirect` and `get_redirect_for_resolution` called it, so every lookup could write.
- **`dtsDirectories`** was on the loader, and the faking vfs kept a copy of it.

Read against the pin, the effects are the same:
- the same calls fill the map, with the same condition (`loader` was set exactly when the
  references are not empty, and only during the load);
- the realpath goes through the same host;
- after the load the map is read only.

So the difference is in structure only. The probe and the gate below confirm that.

**Results.**

The redirect is exercised. In the preserveSymlinks build, Go's trace resolves

## What was ported (`a2f34b0e4`, structural, no behaviour change)

Restructuring was worth it although nothing differed:
- B3's marker for this function named a function that does not exist at the pin;
- every mapper lookup could write;
- the next pin bump diffs Go's builder methods, and those had no Rust counterpart.

The changes:
- **New** `ProjectReferenceFileMapperBuilder` (`// Go: projectreferencefilemapper.go:26`). It is
  `FileLoader::project_references` and holds the shared mapper and the resolution host. It has
  `get_parse_file_redirect` (`:173`), `get_redirect_for_resolution` (`:180`),
  `get_compiler_options_for_file` (`:187`), `get_redirect_parsed_command_line_for_resolution`
  (`:192`) and `resolve_symlink` (`:197`). The loader's six call sites use it; the program's use the
  mapper.
- **New** `ProjectReferenceFileMapper::resolution_host` (`:31`), which makes the faking host.
  `dts_directories` moves into the mapper (Go `dtsDirectories`), and the faking vfs reads it there.
- **Deleted** `get_source_to_dts_if_symlink`, `MapperLoader`, the mapper's `host` and `loader`
  fields, `FileLoader::dts_directories`, and the end-of-load clearing (the mapper keeps no host now,
  so there is no cycle).
- **One deliberate difference from Go's order.** `resolve_symlink` checks its condition
  (`preserveSymlinks`, references) before the map lookup. Only it fills the map, and only when the
  condition holds, so the order changes nothing. A program without `preserveSymlinks` then makes
  no path (an allocation per lookup).
- **Not ported in round 1, and wrongly called unobservable.** Go's builder host is
  `compilerResolutionHost{host, Config.BaseDirectory()}`; round 1 kept the host's current
  directory. That is a real difference from Go, from before B7 (Astra's B7 finding 1). Round 2 fixes it
  (see "Round 2" below).

## Round 2 (Astra's review of `9745f93fa`, `reviews/2026-11-11-astra-b7.md`)

### Finding 1: the loader's base directory (a real difference from Go, from before B7)

**Go.** At the pin the compiler host has no current directory (ts#64159). The loader takes the
config's base directory, `opts.Config.BaseDirectory()`, which is the config file's directory or, for a
program with no config file, the command line's or project's directory. It uses it for:
- the resolution host of its builder and module resolver, `compilerResolutionHost{host,
  Config.BaseDirectory()}` (`fileloader.go:347`). The resolver's base is the fallback of `paths`
  without `pathsBasePath` and of the type roots without a config path (`module/resolver.go:449`,
  `:1452`);
- the automatic type directive names (`:293`) and their containing file (`:279`);
- the lib-replacement lookup (`:980`).

tsc-rs used the compiler host's current directory there, and the config file's directory for `:279`
and `:980`.

**Reproduction** (user-reachable, through the API; `scripts/perf-rearch/parity_api.py probe`):
- `build-paths-base-directory`. The build orchestrator's `compilerOptions` add `paths: {"alias":
  ["./src/value"]}` (no `pathsBasePath`) to `pkg/tsconfig.json`, one directory below the session's.
  `pkg/main.ts` imports `"alias"`, and only `pkg/src/value.ts` exists.
  - Go: the build answer has no diagnostics, status 0.
  - tsc-rs at `4ae5301b0`: TS2307 "Cannot find module 'alias'" at `pkg/main.ts`, status 2, and a
    different `tsbuildinfo`.
  - This is Astra's case: base `pkg/`, host directory the session's.
- `programs-config-path-base-directory`. A `createPrograms` program whose options name
  `configFilePath: pkg/tsconfig.json`, with `types: ["foo"]`, `lib: ["es5"]` and `libReplacement`.
  Both packages are only in `pkg/node_modules`. Its base directory is still the session's.
  - Go: `pkg/main.ts` and `globals.d.ts` only, and TS2688 "Cannot find type definition file for
    'foo'".
  - tsc-rs at `4ae5301b0`: it also loads `pkg/node_modules/@typescript/lib-es5/index.d.ts` and
    `pkg/node_modules/foo/index.d.ts`, with no TS2688.
- Both are now permanent api items. At `4ae5301b0` both are DIFF; from `1fbe71329` on, both MATCH.

**Fix** (`1fbe71329`):
- `config_base_directory` (Go `Config.BaseDirectory()`; `NewProgram::base_directory`'s rule, now
  shared) gives the base.
- `CompilerResolutionHost::new(host, base_directory)` is Go's `compilerResolutionHost`. The builder
  passes the base, so the loader's resolver and the program, which keeps that resolver (Go
  `program.newResolver`, `program.go:193`), resolve from it.
- `add_automatic_type_directive_tasks` and `resolve_automatic_type_directives` use the base, and
  `get_inferred_library_name_resolve_from(base, name)` takes Go's signature.
- The parse workers' resolvers take the same base (`WorkerResolveConfig::base_directory`). Before,
  their answers could differ from the loader's in such a case. The early pool's config gives the
  same base, so it is still taken.

**The same mistake elsewhere:** every `BaseDirectory()` / `GetCurrentDirectory()` call of Go at the pin
outside the API and tests, checked against its Rust counterpart:

### Finding 2: a query after the build

`api/build-symlink-monorepo` now runs these steps:
1. `createSnapshot` opening b and b-preserve, then `getSourceFileNames`, the program, semantic and
   declaration diagnostics, and `emitToString` of each;
2. the build orchestrator, built twice;
3. **in the same session** (`afterBuild`, new in `parity_api_session.py`):
   - (a) `updateSnapshot` with `fileNotifications.invalidateAll` and `ensurePrograms`, then the same
     queries of both projects. Go reports no changed project here: the project service uses the
     sources, and the build changed only outputs. `resolveSymlink` now reads the real built
     `node_modules/a/dist/*.d.ts` through the faking host.
   - (b) `updateSnapshot` closing b and editing `packages/b/src/index.ts` through a layer
     (`fileNotifications.changed`, `ensurePrograms`). The edit adds
     `export const crossed: string = wrap(builtInner.v)`. b-preserve's program is updated
     incrementally (Go: `changedProjects` with that one file), and `getSemanticDiagnostics` reports
     TS2322 "Type 'Inner' is not assignable to type 'string'": a's type, through the redirect. The
     replaced snapshot is released.

b is closed in (b) because Go writes `changedProjects` (a map) in random order: with both projects
changed, Go's own two runs differed in bytes, and the tier made the item GO-BROKEN.
