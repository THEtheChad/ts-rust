## 0. Recommendation

**Go.**
- **Gain:**
  - The split alone takes wall from the default to −53% on vscode, −32% on t3-server and −31% on umami (M).
  - That puts vscode at 0.30× Go and t3-server at 0.26× (M).
  - Count-only switches add nothing to wall (M).
- **Partition:** use splits that **refine Go's 4-way split**. In a refinement each fast checker checks a subsequence, in Go's order, of one Go checker's files.
  - That makes every fast checker colder than its Go checker at every file. That removes Astra's finding 8 by construction (A) and makes the hard-limit monitor complete under one stated assumption (A1, §3.1).
  - The cost in balance is small: 0.89–0.93× of Go-16's critical path on the types proxy (E, §2).
- **Certification and fallback are per Go group.** Each group's outputs depend only on its own Go checker, so a fire reruns only that group.
- **Drop lazy members and never-order from certified mode.** They buy 0% wall, and they break the "colder than Go" property that the design relies on.
- **What stays empirical:**
  - A1 itself;
  - the order of type ids, mainly the id tests in `is_deeply_nested_type`;
  - the claim that tied types which are observationally equal can be swapped;
  - once-only guards in the checker.

  §3.8 lists them, and §6 says how each one is tested.

## 2. Partition policy

**Go's split** at the pin is FENNEL-style streaming with import affinity, capped at 101% of the average estimated weight (`program/ls_program.rs:817`, `:987`). Each checker checks its files in program order (`program.rs:5236`, the association filter). Today `--checkers N` and `--fast` use Go's N-way split (`program.rs:4210`, `:4244`), which is **not** a refinement of the 4-way split.

**Refinement.** Let Go checker *i* check `F_i = (f_1 … f_m)` in program order. A refinement splits `F_i` across sub-checkers `c_{i,1..k_i}`, each checking a subsequence of `F_i` in that order. When sub-checker *c* reaches file *f*, the files it has checked are a subset of the files Go checker *i* has checked before *f*. Checking is deterministic, so *c*'s caches hold a subset of what Go's have (lemma R).

**Why refinement helps soundness** (A, given A1 in §3.1):
1. **The fast run is never warmer than Go.** Go can't skip work through caches that the fast run did not also do. Astra's finding 8 (a fast run that skipped the work that makes Go hit a limit) then cannot happen. The limit monitor at Go's own hard limits is complete. The D0-1B shadows become validation checks of A1, not production triggers. Without refinement, c1, c2 and Go's 8- and 16-way splits can be warmer than Go: zod and `chain-one-warmer` show this. Shadows are then required, and they remain estimates.
2. **Each fast checker maps to one Go checker.** "Which checker would report this diagnostic in Go?" then has an exact answer, the group. That makes cross-file repair and cycle reconciliation exact (§3).
3. **Fallback can be per group** (§4).

**Cost in balance** (E, `scripts/perf-rearch/d1/refine_sim.py` on the logs from `run-calllog.sh`):
- Method: split each c4 group 4 ways, files longest-first by their c16 cost.
- **Types-created proxy:** the refinement's critical path is 0.90× (vscode), 0.89× (t3-server), 0.93× (umami) and 0.91× (hono) of Go-16's.
- **Instantiation proxy:** 1.23× (vscode), 0.94×, 0.71× and 0.97×.
- **Caveats:** both are CPU proxies, and the costs come from an oracle (the real split must use estimated weights).
- **Imbalance:** the c4 groups are imbalanced by 1.05–1.58× max/mean (types). Sub-splitting can't move work between groups, so the policy needs dynamic help (below).
- **Kill check:** stage S1 measures the real wall of a refinement against Go-N. It goes ahead only if the refinement reaches at least 90% of Go-N's gain.

**Policy:**
1. **Count N.** `N = min(physical cores, N_max, max(4, ceil(checked_weight / W)), memory cap)`.
   - `N_max = 16` when Go's own test `should_prioritize_source_files` is true (source-dominated, like vscode), else 12. This is based on the c12/c16 data and on how declaration types duplicate.
   - Memory cap: estimated RSS at most 50% of MemAvailable, using +0.10–0.23 GB per extra checker (M, vscode and t3-server).
   - Physical cores, not SMT threads (`fast_mode.rs:198` uses `available_parallelism`, which is 32 here).
   - `W` is tuned so hono-size projects get about 8–12. The exact value is a stage S1 sweep.
2. **Checkers per group.** `k_i` from largest-remainder rounding of N in proportion to estimated group weight. Go's weights are balanced to 1%, so normally `k_i = N/4`.
3. **Inside a group.** `fast_mode::cost_split` (`fast_mode.rs:236`, import affinity, `dep_share` 100) restricted to the group's files. Each sub-checker then checks its files in Go order. A/B this against contiguous runs in program order (locality) in S1.
4. **Monotone stealing inside a group.**
   - An idle sub-checker of group *i* may take an unstarted file *f* from a group-mate only if *f* comes after every file it has already checked, in Go order. It takes from the tail of the most-loaded group-mate.
   - Every schedule is still a refinement, so certification holds and the output stays deterministic even though the schedule is not.
   - Today's stealing (`program.rs:5291`) breaks refinement and is not certifiable.
5. **Tail split across groups.** An idle worker may start a fresh checker for group *j* and take the tail of *j*'s largest queue. A fresh state is a subset of any state, so this is still a refinement. Only when the estimated tail is larger than about 3× the fixed cost of a new checker. This fixes imbalance between groups.
6. **Exact only (no certification):**
   - printed counts (`--diagnostics`, `--extendedDiagnostics`), `--generateTrace`, `--singleThreaded` and an explicit `--checkers`;
   - LSP and API;
   - watch mode until a later stage.

## 3. Monitor completeness

### 3.1 The assumption everything rests on

**A1, deterministic demand:**
- A memo entry (type, link, relation result, resolved signature) demands the same sub-entries every time it is computed. Caches only short-circuit the work.
- Corollary 1: from a colder state, the check of a file computes a superset of what it computes from a warmer state, in the same relative order.
- Corollary 2: along any demand path, instantiation depth, the per-statement count and relation depth are at least as large from the colder state.

A1 fails only through order-sensitive events: limits, cycle poisoning, id-order tests, symbol-id uses. Those are what the monitor watches. A1 is **empirical**. §3.8 lists the mechanisms known to strain it, and §6 tests it directly.

### 3.2 Limits: complete under refinement and A1, so no shadow is needed

The fast run is colder, so if it doesn't reach a limit, Go doesn't either (corollary 2). If the fast run does reach a limit, the group falls back.

| limit | site |
|---|---|
| instantiation depth 100 and count 5M | `checker/checker_p24.rs:2079`, handler at `:2150` |
| conditional tail 1000 | `checker_p27.rs:270` |
| relation budget | `relater_p1.rs:964` (start), `relater_p4.rs:705` (`relation_count <= 0`), `inference_p2.rs:732` |
| relation stack 100 | `relater_p4.rs:738` |
| constraint depth 100 | `checker_p30.rs:1110` |
| complexity sites | the spike's `Complexity` hooks |

**Margins:**
- Production fires at the hard limits. D0-1B: 1 of 8 large configs fires, zod, which is also Go's own limit hit.
- Validation builds also fire at margins (depth 90, count 4.5M, relation depth 90) and log how often a margin is crossed without the limit being reached. That is the A1 "near miss" metric.

**Per-statement count:** under refinement this is just the trap at 5M. In the spike, t3-server's peak was 3.9M, the same in every split (M, D0-1B).

### 3.3 Shadows: validation builds only (`cert-shadow` cargo feature)

These are for testing A1, for any future non-refinement split and for count-only switches.

**Instantiation height** (vdepth): D0-1B's version (`partition_monitor.rs`, `frame_end` and `cache_hit`), kept as it is.

**Per-statement count** (vcount):
- Each instantiation result created at or after `first_dynamic_type` records `cold_cost`: the misses in its frame plus the `cold_cost` of every distinct cached result it used.
- For each statement, vcount is the real count plus `cold_cost(r)` for each result made before the current file, charged the first time it is used in that file (later uses are hits from the same file in a cold checker too). The total saturates at 5M.
- This overcounts shared sub-DAGs, so it errs toward firing (safe).
- The reset points are `checker_p03.rs:318`, `:677` and `checker_p09.rs:50`.

**Relation height:**
- A side table, keyed like `Relation` (`relater_p1.rs:318`: plain, `plain_wide`, generic), holds `(height: u8, budget_used: u32)` for each entry when it is written.
- A hit on an entry from before the current file adds `depth + height` to the virtual relation depth and `budget_used` to the virtual budget.
- Fire when the virtual depth is 100 or more, or the virtual budget runs out.
- The side table keeps the off-mode `Relation` layout unchanged.

**Lazily resolved links:**
- A frame around every memoized link resolution:
  - symbol type, declared type, resolved members (`resolveStructuredTypeMembers`), base types, type arguments of deferred references, resolved signatures and return types;
  - type parameter constraints and defaults.
- Each frame records `(inst_height, inst_cost, rel_height)` in a side map keyed by (link kind, key).
- A read of a cached link from before the current file adds the same contributions as an instantiation hit.
- This needs about 25 sites. Its cost is why it stays behind the feature.

### 3.4 Cycles: fire only when group-mates disagree

The brief's narrowing, "only when the cycle produces a diagnostic", is **not enough**. With `noImplicitAny` off, a circularity silently becomes `any` (7022–7024 are not reported), and that `any` can reach d.ts output or other diagnostics.

**Rule:**
- At every circularity outcome site, the certified checker records a *phantom outcome* whether or not an error is reported: `(kind, stable key of the target, report node)`. The sites are where `pop_type_resolution` returns false and Go takes the circular branch: type alias 2456, 2502, base types 2506/2310, 2313, implicit-any circularity and the default-parameter cycle (`checker_p24.rs:1735`).
- The stable key is the binder symbol, or for checker-local types and signatures (`TypeSystemEntity`, `checker_p21.rs:209`) the declaration node of their symbol. No stable key: fire.
- After the check, for each Go group and each key in the union of its sub-checkers' outcome sets, collect from every sub-checker that **resolved** that target (its link is set) whether it took a circular outcome, and which one.
- **Fire if they disagree,** or if some resolved the target without a cycle while others hit one.

**Why this catches every output-changing cycle** (A, under A1):
- Let *e\** be the first file, in Go's group order, that demands target T, and *X* the computation there that demands it.
- The sub-checker containing *e\** computes everything Go computes before *X* (corollary 1). The extra computations it does are ones that were cached in Go. None of them demands T, or Go would have demanded T earlier.
- So that sub-checker enters T through *X*, with the same resolution stack above *X*.
- A cycle participant U that Go had already resolved would also have demanded T, again earlier than *X*. So the participants' states match too.
- That sub-checker therefore reproduces Go's outcome. Every other sub-checker that resolved T either agrees (its observables match Go) or disagrees (the rule fires).

**Signature and contextual sentinels** (`checker_p09.rs:1549`, `checker_p32.rs:1473`; 37,770 events per run on t3-server) are **not** triggers. They are re-entries of one node inside that node's own resolution, so by the same argument the result is fixed once the outer entry is fixed. A cross-interaction through another declaration shows up as a `push_type_resolution` cycle, which is covered. This is empirical; there are fixtures in §6.

### 3.5 Cross-file diagnostics: repair instead of falling back

In Go, file *g*'s diagnostics are everything Go checker *i* added to *g*'s file, while checking any of its files (`checker_p15.rs:1753`, collection-wide).

**Rule:**
- At each file end the checker already scans the stored diagnostics (`checker_p03.rs:229`; the spike's `stored_since`).
- For *g*, the certified output is the union, sorted and deduplicated, of the diagnostics into *g* from every sub-checker of group(*g*). This repairs the result rather than falling back.
- **Fire only on variants:** two members of the union with the same `(file, start, length, code)` but different message chains or related information. That case comes from #4825: a later add mutates the stored diagnostic, for example by adding related information.

**Why this is complete** (A, under A1):
- Each diagnostic Go adds into *g* is added during some file *e* of the group. The sub-checker containing *e* adds it too: it computes a superset, and the first demand happens at the same point.
- Anything extra that a colder sub-checker adds was also added in Go at an earlier first demand, so the union equals Go's set.
- Diagnostics into *g* from checkers of other groups are dropped, as in Go.

Global diagnostics (`checker_p15.rs:1777`, deferred callbacks included) get the same union and variant check, across all checkers.

This replaces D0-1B's `cross_file_diag` trigger (168 of 633 runs fired), and in clean runs it should fire close to 0% (E).

### 3.6 Id ties

**The brief's narrowing, "only for types made in different files' checks", is unsound by itself.**
- Counterexample: Go checker *i* creates *t₂* while checking an earlier file *e* that belongs to group-mate *c′*, and creates *t₁* at *f*. So in Go *t₂* < *t₁*.
- Sub-checker *c* creates both at *f*, in the order *f* demands them, possibly *t₁* < *t₂*.
- Both were "made in the same file" in *c*, yet the order is flipped.

The right axis is whether *c* is the group's earliest creator of both types. By the argument in §3.4, an earliest creator reproduces Go's order. Deciding that needs identities that are stable across checkers (fingerprints).

**Design:**
1. **`compare_types` id fallback** (`utilities/utilities_p1.rs:1173`; 256k per run on vscode):
   - A tie there means every compared child is identical (`compare_types` returns 0 only for `t1 == t2`). The two types are the same recipe with two identities.
   - **Fire only if they can be told apart**: they differ in flags, object flags (freshness included) or alias.
   - Claim E (**empirical**): same recipe, flags and alias means the two types print and relate identically. Under claim E, their order can't change the output.
2. **`compare_symbols` fallback** (`:722`; no declarations, same name): fire unless the two symbols have equal flags, check flags and resolved types. Read only links that are already resolved; if one isn't, fire.
3. **`is_deeply_nested_type` id test** (`relater_p1.rs:2010`, `:2077`, `inference_p1.rs`; Astra's ordered-id case):
   - Assumption A3 (**empirical**, the same intuition as corollary 2): a colder checker has at least as many increasing-id matches on a recursion stack.
   - Under A3, "false only because of the id order" (`deep_flip`) is safe, because Go would also say false.
   - `deep_true` (483 of 633 runs; 33.7k per effect run) **cannot** be a trigger, and it remains the largest empirical residue.
4. **Fingerprint reconciliation** (option, stage S3b), only if the "can be told apart" rate is too high:
   - For each fired tie, compute a structural fingerprint that is stable across checkers. It bottoms out at binder symbols and declaration nodes.
   - At the barrier, ask the group-mates for their creation position of that fingerprint, in Go order (built from an index of their types by (flags, symbol, kind)).
   - Re-evaluate the comparison in the "virtual Go order".
   - Estimated cost: tens of ms per checker at the end of the run.

### 3.7 Late-bound names and symbol ids

Each worker counts symbol ids on its own (`program.rs:4348`), so a sub-checker's ids differ from its Go checker's.

**Late-bound names:**
- The node builder adds the length of a `__@name@<id>` name (`checker/nodebuilder_impl_p3.rs:771–778`).
- **Narrowed trigger:** keep a count *n* of late-bound names counted in the node-builder context. At each truncation test, fire only if `|approximate_length − limit| ≤ 9·n`.
- This is sound: an id has 1 to 10 digits, so the difference per name is at most 9.

## 4. Fallback

**Unit of fallback: the Go group.**
- Outputs for group *i*'s files (diagnostics, declaration diagnostics, emit) depend only on Go checker *i*.
- Global diagnostics are a union over checkers, and late-bound ids come per worker from its seed.
- On a fire in any sub-checker of *i*, set group *i*'s cancel flag. Its sub-checkers stop at the next cancellation check (`is_canceled`/`was_canceled`, `checker_p03.rs:295`; `utilities_p2.rs:1326`) and are thrown away.
- A **fresh** exact checker `new_pool_checker(i, 4)` (`program.rs:4348`) is built from a **saved clone of the `WorkerSeed`** taken at pool start (`program.rs:4154`). It checks all of `F_i` in program order, then runs group *i*'s global and declaration diagnostics and emit.
- Other groups keep their certified results.

**Fresh state:**
- An audit (S2) lists the shared state that sub-checkers change: synthetic seeds, id seeds and skips, lazily published shared tables, and `file_associations` (a `OnceLock` that asserts "checker pool made twice", `program.rs:4279`). The last must become a per-pool table holding both the Go group map and the sub-checker map.
- **Proof tool:** `GOPORT_CERT_VERIFY=1` runs the fallback group in a separate process with the exact pool and compares bytes (like A1's isolated verify).
- Re-exec of the whole process is the last resort when the seed can't be cloned (for example wasm).

**Buffered output:**
- Nothing that depends on the checkers is printed or written until every group is certified or redone.
- B1 already holds writes (`emitter/program_emit.rs:211`, `DeferredWrites`). `open` becomes conditional on the certificate. A fallback group's held writes are dropped and that group re-emits.
- Stdout from the start of the check is buffered as well.
- The monitor stays on through global diagnostics, declaration diagnostics and emit. Emit runs on a sub-checker that is colder than Go's emit-time checker, so §3 applies unchanged.

**Wasted work bound:**
- `wall ≤ max over groups of (certified: that group's sub-checker finish time; fired: t_fire(i) + T_exact(i))`.
- `T_exact(i)` is at most the default's check time.
- **Worst case:** a fire at the very end costs about `T_fast + T_default_check`. That is about +40% on vscode (E), and nothing seen so far fires on vscode.
- **zod** (always fires): D0-1B's first limit event has a median at 17–19% of the run. Estimate (E): about the default wall plus 5–10%.
- Start the exact checker as soon as the group fires, on a thread freed by its cancelled sub-checkers. Nothing speculative runs in advance.

**`--incremental`:**
- `.tsbuildinfo` stores certified (equal to Go's) per-file diagnostics and signatures.
- A warm build checks only the affected files of each Go group, in order. A refinement of that subset is still covered by lemma R.
- N scales with the affected checked weight, so small rebuilds stay at 4.

**`-b`:** certify per project; hold each project's writes until its certificate, and downstream waits as it does today. `-b` already checks projects concurrently, so this is a later stage (it keeps Go's 4 now, `fast_mode.rs:198`).

## 5. Zero off-mode cost

Once certified mode is the default, "off" means the exact path: fallback, explicit `--checkers`, printed counts.

**Bar:** exact mode within +0.02% of user-space instructions of the parent commit, on vscode, t3-server, umami, hono and zod, with `--singleThreaded`, 3 interleaved runs, `--profile goport`, and the lib blobs and CGU traps handled (brief).

The spike costs +0.18–0.35% because of hooks on hot paths: `on_instantiation` and `frame_end` on every miss, `cache_hit` on every hit, `on_relation_done`, and `matches` counters inside the deep-nesting loops.

**Design:**
1. **Trap thresholds:** limits stay as they are, and the certified hook sits only in the cold limit handlers (`checker_p24.rs:2150`, …), as one `if self.cert.is_some()`. Validation margins come from limit fields set when the checker is made; production keeps the constants. **No hot-path instruction is added.**
2. **Hooks only in cold branches:**
   - cycle found (`checker_p21.rs:217`) and circularity report sites;
   - the tie fallbacks (`utilities_p1.rs:1173`, `:722`), which are already the last branch;
   - the late-bound branch of the node builder (`:771`);
   - file boundaries (`checker_p03.rs:229`);
   - the `deep_true` return path only. No counting inside the loops: the recount runs in a cold helper.
3. **Shadows only behind the `cert-shadow` cargo feature,** never in shipped builds.
4. **No generic `Checker<const CERT: bool>`:** it would double the codegen of the checker.

Certified mode's own overhead should be at most 1% CPU (E), with shadows off.

## 6. Validation plan to reach "zero divergences at scale"

**Inputs:**
1. **Projects:** the parity set, 10 projects × 22 configs × {noemit, emit}, through the D0 driver. Add t3-web and any larger repo set that is available.
2. **Compiler corpus:** the 1,719 multi-file cases. Single-file cases can't depend on the split.
3. **Fuzzer:** `parity_fuzz.py` / `vendor/difffuzz` mutators on multi-file seeds.
4. **Adversarial generators,** extending `scripts/perf-rearch/d0/make_fixtures.py`. Each family has random parameters (segments, placement, file order, `noImplicitAny` on and off), at least 200 instances each:
   - **limit warmers:** chain-deferred, chain-one-warmer, count-split, tail-split, plus relation-depth and relation-budget warmers (deep structural comparisons cached in another file);
   - **link warmers:** symbol type, members, base types and deferred type arguments resolved in another file;
   - **cycle entry:** cycles of 2–5 participants across 2–5 files, entered from each file; alias, base, return-inference and default cycles;
   - **cross-file mutation:** #4825 related information added to a stored diagnostic;
   - **ordered-id recursion:** recursive generics created in reverse order in a warmer file;
   - **id ties:** same-declaration anonymous types and fresh against regular types, made in different files;
   - **late-bound names:** within 0–20 of the truncation limit, with symbol-id padding across 999/1000 and 9999/10000;
   - **once-only guards:** from the S3 audit.

**Partitions and seeds:**
- Per input: the policy partition at N = 8, 12 and 16.
- Plus R random refinements: random `k_i` from 1 to 8, random sub-assignment, and stealing schedules from a seeded deterministic scheduler. R = 16 for projects, 8 for the rest.
- In validation builds, add 4 random non-refinement partitions with shadows on.
- **Order-perturbation runs:** a validation switch that reverses the id fallback for ties that can't be told apart, and seeds random orders in the deep-nesting id test for types made in different files. Outputs that never change across seeds measure claim E and A3 empirically.

**What counts as a pass:**
- Every certified run is byte-identical to the exact run of the same bin, on stdout, stderr, exit code, emitted files and `.tsbuildinfo`. The exact run already matches Go through the parity gate.
- Every fallback run is identical too.
- In validation mode the raw, uncertified output is also kept. **Every raw divergence must have fired**; one that didn't is a miss.
- **Mutation testing:** with any one trigger or repair disabled, the adversarial set must produce at least one miss; otherwise the set doesn't test that trigger.
- **Volume:** at least 300k certified runs with zero misses. By the rule of three, the 95% upper bound on the miss rate is then 1e-5 per run.
  - Rough mix: about 8k project runs, 19k corpus runs, 100k fuzz runs and about 110k adversarial runs.
  - That is 3–5 days of machine time. It isn't timing, so it can run while the machine is busy.

**Kill conditions:**

| condition | action |
|---|---|
| A miss whose mechanism no trigger covers with an argument beyond A1 | stop; report to Chad |
| A1 near misses (margin crossed, or the shadow disagrees with the exact run under refinement) in more than 0.1% of runs | stop, and also lower the production margins |
| Fallback rate above 30% of large configs at the policy partition | stop |
| Certified end-to-end gain under 15% median on large projects, idle | stop |
| Exact mode above +0.02% instructions, or certified mode above 2% CPU | stop |
| Ties that can be told apart fire in more than 10% of large configs | build S3b (fingerprints), or kill |

## 7. Staged implementation

Each stage is mergeable, with parity full OK on the default.

No monitor. | 250–400 lines | Off by default, so parity full and icount unchanged. D0-1A-style output-identity rates under refinement. Timing against Go-N; **go only if ≥90% of Go-N's gain** |

Total: about 2,500–3,500 lines of production code and tools, 5–8 weeks. Most of that is validation.

**Risks:**
- **A1 is the foundation.** The most likely real breaks are once-only guards and first-creation metadata. S3's audit and the near-miss metric target them.
- **Memory:** RSS +21% to +44% at 12–16 checkers; the policy caps N by memory.
- **CPU:** +32% to +53%, which hurts parallel builds and small CI runners. The policy uses the cores actually available.
- **Fallback freshness:** any shared state that is missed makes the fallback differ from Go. The isolated verify is required before S2 merges.
- **`deep_true`** is unbounded by triggers, so the order-perturbation evidence carries it.
- **Upside over `--fast`:** certified output doesn't depend on N or the machine, which `--fast` doesn't guarantee today (README).
