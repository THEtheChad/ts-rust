## Finding

**Medium: a literal `<line>` collides with a normalized stderr**
(`parity_grandfather.py:143`, hashed at line 148).

- **Problem:** a stderr ending in `\t<file>.rs:<line>` doesn't match `SITE`,
  so it is hashed as it is. It then gets the same `stderrSite` as a crash at
  any numeric line.
- **Effect:** run through the real fuzz, regen, match and compare paths, such
  a case came out GRANDFATHERED with PARITY OK, against all 9 crash pins.
- **Fix:** domain-tag the hash, bump the format, re-pin, and add the negative
  control. Root fixed this in version 4; see `parity.md`, "Version 4".

## What was confirmed

- **Normalization:** only the final numeric site changes. The checks that
  still reject a crash:
  - a different panic text;
  - a signal line;
  - extra output;
  - a different exit code.

  Windows paths, CRLF and a missing or extra trailing newline are left
  unnormalized, which is the conservative choice.
- **Re-pin:** sound. Only `stderr` → `stderrSite` and the evidence changed.
  The provenance hashes match.
- **Versioning:** each format version rejects the other, and a missing
  `stderrSite` fails in both full and quick runs.
- **Self-tests:** they use the production code paths.
- **Saved full gate:** re-compared independently: 187,194 items, 0 lost,
  PARITY OK.
